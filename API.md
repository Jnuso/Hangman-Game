# Hangman REST API

The Flask server owns the word, game rules, and game state. All API responses are
JSON, including HTTP errors. Responses use `Cache-Control: no-store`. The root
page and static assets use their corresponding HTML/CSS/JavaScript types.

## Start locally

From the repository root after installing `requirements.txt`:

```powershell
.\.venv\Scripts\python.exe server.py
```

The development server listens at `http://127.0.0.1:5000` with debug disabled.
Open `/` to play in the browser, or use the JSON endpoints below. This command is
for local development. The deployed application uses Gunicorn; see README for
production configuration and the public HTTPS URL.

## Create a game

`POST /api/games` requires `Content-Type: application/json` and exactly one field:

```json
{"difficulty":"easy"}
```

Difficulty is `easy`, `medium`, or `hard`, ignoring case and surrounding spaces.
There is no implicit default. Additional fields, including `word`, are rejected.

Returns **201 Created**, with a `Location: /api/games/{game_id}` header and state
like the following (the ID and pattern length vary):

```json
{
  "game_id": "0123456789abcdef0123456789abcdef",
  "difficulty": "easy",
  "pattern": "_ _ _ _ _",
  "guessed_letters": [],
  "incorrect_letters": [],
  "remaining_guesses": 6,
  "status": "playing"
}
```

The identifier is generated by the server using UUID4 and represented by 32
lowercase hexadecimal characters. The value above is illustrative; use the ID
returned by your own creation request. Clients cannot choose it.

## Retrieve state

`GET /api/games/{game_id}` returns **200 OK** and current public state.
Unknown IDs return **404 Not Found**.

## Submit a guess

`POST /api/games/{game_id}/guess` requires JSON containing exactly `letter`:

```json
{"letter":"p"}
```

Accepted letters are a single ASCII A–Z character, normalized to lowercase.
Whitespace around a guess is rejected. A valid guess returns **200 OK** and
updated state, including the same game ID. Repeated letters return **409 Conflict**
without consuming a life. Post-game guesses also return **409**.

While playing, `word` is absent from the response. After winning or losing, state
includes `word` and status `won` or `lost`. An incorrect guess consumes one of six
lives; correct guesses reveal all occurrences and consume no lives.

## Errors

Every error has this shape:

```json
{"error":{"code":"duplicate_guess","message":"The letter 'p' has already been guessed."}}
```

| HTTP status | Error code | Meaning |
| --- | --- | --- |
| 400 | `bad_request` | Malformed JSON, non-object JSON, missing or additional fields |
| 400 | `invalid_difficulty` | Unsupported difficulty value or type |
| 400 | `invalid_guess` | Unsupported letter value or type |
| 404 | `not_found` | Unknown game ID or route |
| 405 | `method_not_allowed` | Wrong HTTP method; the Allow header is preserved |
| 409 | `duplicate_guess` | Letter already guessed, ignoring case |
| 409 | `game_finished` | Game has already ended |
| 413 | `request_entity_too_large` | Body exceeds 16 KiB |
| 415 | `unsupported_media_type` | Missing or non-JSON Content-Type |

For guesses, unknown IDs are checked before body validation. For existing games,
body structure is validated before the engine checks completion or letter content.
Rejected guesses do not change game state. No request can override the word,
difficulty, remaining lives, or status of an existing game.

## PowerShell example

With the local server running in another terminal:

```powershell
$base = 'http://127.0.0.1:5000'
$game = Invoke-RestMethod -Uri "$base/api/games" -Method Post -ContentType 'application/json' -Body '{"difficulty":"easy"}'
Invoke-RestMethod -Uri "$base/api/games/$($game.game_id)"
Invoke-RestMethod -Uri "$base/api/games/$($game.game_id)/guess" -Method Post -ContentType 'application/json' -Body '{"letter":"p"}'
```

To target the deployed service, set `$base` to
`https://jnuso-hangman-game.onrender.com` before running the creation request.

## Storage and scope

Each application instance has its own dictionary of games. A lock protects
reads and updates within a process, including simultaneous guesses. Request
bodies are read outside that lock so a slow upload does not block other game
operations. Unknown IDs are rejected before reading the body; after reading it,
the server checks the game again and applies the guess against its current state
under the lock. A restart clears games, and multiple processes do not share
storage: use a single worker
until shared storage is introduced. Games currently remain in memory until the
process restarts; expiration and persistence are not implemented.

There is no login or per-player ownership: anyone with a game ID can interact
with that game. Browser assets are served from `/static/` and the page from `/`.
Word lists and Python source are not exposed as static routes.
